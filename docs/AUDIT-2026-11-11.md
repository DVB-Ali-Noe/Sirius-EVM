# Audit de sécurité — 11 novembre 2026

Audit en deux passes sur le code local (branche de travail, non déployé). Aucune modification applicative, aucune commande Git, aucun secret lu, aucun réseau distant : les reproductions ont tourné sur Hardhat local (`127.0.0.1`, chainId 46630 via `SIRIUS_LOCAL_BILLING_TEST`), SQLite jetable et modules réels du dépôt (`--conditions=react-server`). Les scripts de preuve étaient jetables (répertoire temporaire hors dépôt, nettoyés) ; les commandes et assertions clés sont reproduites ci-dessous pour rester vérifiables.

Méthode : passe 1 = cartographie et analyse statique (surface d'attaque, scanner, contrats, web/auth, règlement, uploads, TEE) ; passe 2 = contre-analyse et reproduction de chaque candidat avec les vrais modules, contrôles négatifs obligatoires (témoin sain par reproduction), exécutée par un agent GLM‑5.3 supervisé, puis re-vérification ligne par ligne des gardes citées.

## Verdict global

Aucun finding CRITICAL. **2 HIGH, 6 MEDIUM, 3 LOW, 2 INFO**, tous reproduits ou tracés fichier:ligne. La chaîne de confiance TEE/RA-TLS n'a pas de contournement exploitable (fail-closed vérifié à chaque étage). Les profils de sécurité coûteux (auth, anti-rejeu, crypto, CSP, conteneurs, contrats v7) tiennent leurs promesses ; les failles confirmées se concentrent sur les états concurrents des uploads chunkés, l'échantillonnage mémoire du runner, la réconciliation des règlements face à un `release` concurrent, et deux parcours de démonstration (assistant, KYB).

## Findings confirmés

### [HIGH] U1 — OOM du runner à l'échantillonnage d'un gros dataset

- **Vecteur** : fournisseur authentifié publie un CSV en morceaux avec `chunkBytes = 64 Mio` (choix client autorisé, `src/lib/upload/chunked.ts:22,121-130`), lignes courtes (64 Mio ⇒ ~16,7 M lignes). Le scellement en flux réussit ; au premier entraînement, `completeLines` matérialise toutes les lignes du morceau (`split("\n").map()`, `src/lib/tee/chunked-sample.ts:124-135`), bornes appliquées seulement après (`:193-199`), cache des morceaux en clair (`:145-158`). Le tout dans le processus runner (tas 384 Mio, `Dockerfile.runner:35`), avant tout worker (`src/lib/tee/core.ts:140`).
- **Preuve** : enfant borné `--max-old-space-size=384`, vraies fonctions chiffrement/scellement/échantillonnage. Sortie : `SEALED` puis `FATAL ERROR: … heap out of memory`, pile `Runtime_StringSplit ← StringPrototypeSplit`, exit 134, RSS 1,06 Go. Contrôles : morceaux 64 Kio → succès (RSS 320 Mo) ; morceau 64 Mio à lignes longues → succès. L'OOM dépend du nombre de lignes matérialisées, pas de la taille seule.
- **Impact** : crash du runner au premier prêt sur le dataset, boucle au redémarrage CVM (coût fournisseur Phala à chaque cycle). Variante déduite non testée : 1 Gio en morceaux 64 Mio ⇒ 512 Mio dans le cache `plain`.
- **Remédiation** : échantillonner en flux sans tableaux intermédiaires, appliquer les bornes pendant la lecture, évincer les morceaux consommés ; isoler la préparation dans le worker borné.

### [HIGH] F1 — `release` concurrent : paiement sans prestation, rejeu impossible

- **Vecteur** : `release` est permissionless (`contracts/src/SiriusEscrowV7.sol:250-261`). Le runner journalise sa transaction signée avant diffusion (`src/lib/runner/budget-transaction.ts:84-90`). Si un `release(loanKey, preimage)` concurrent est inclus d'abord, la tx runner revert (`LoanNotLocked`), l'opération passe `failed` au journal réel (`:113-114`), et toute reprise est refusée (« Tentative de règlement épuisée », `:71`). `settleBilledEscrow` saute la réconciliation métier dès qu'une entrée de journal existe (`src/lib/billing/settlement.ts:93-99`) ; la prestation (échéance de prolongation, crédits de pack, pass d'accès API) n'est appliquée qu'après un retour réussi (`src/runner/handler.ts:781-789,856-867`).
- **Preuve** (Hardhat local, fixture de `src/lib/billing/flow.test.ts`) : release du tiers inclus bloc 16, tx runner reverted bloc 17 ; on-chain `Released`, provider crédité ; réponse 502 « Règlement on-chain rejeté » ; rejeu 503 ; échéance jamais repoussée (témoin sain : +1 jour). Le prêt ordinaire possède un fallback distinct (`src/lib/sirius/settle.ts:418-419`) ; le blocage concerne prolongations, packs et passes.
- **Conditions réelles** : le front-run mempool n'est pas établi (Robinhood Chain = Nitro FCFS, séquenceur privé). Mais le même état est atteignable sans adversaire : la procédure de reprise documentée (`docs/passage-mainnet/20-finalite-rapide.md:137-140`) rediffuse un `release` depuis n'importe quel wallet, et un `release` runner « perdu puis retrouvé » (rejeu après coupure) entre dans ce cas. Défaut opérationnel réel.
- **Amplification (F1-bis, démontrée)** : un seul événement compte 3 échecs au coupe-circuit (`src/lib/runner/budget-ledger.ts:493-501`) ; avec `maxFailures ≤ 3`, un seul `release` concurrent bloque tous les nouveaux devis et règlements jusqu'à intervention opérateur.
- **Remédiation** : réconcilier le `release` canonique même quand une entrée de journal existe ou est `failed` — un prêt on-chain `Released` avec le bon `termsHash` doit clôturer idempotemment la prestation ; ne pas confondre échec du hash runner et échec du paiement.

### [MEDIUM] U4 — Annulation perdante supprime le stockage d'un dataset publié

- **Vecteur** : DELETE concurrent d'une clôture. `abortDatasetUpload` contrôle un instantané d'état (`src/lib/sirius/chunked-upload.ts:596-607`) ; `abortUpload` exécute le CAS `updateMany` **sans lire son count**, puis `deletePrefix` inconditionnel (`:219-227`). La clôture passe SEALING→SEALED entre les deux : l'annulation perdante supprime quand même morceaux et manifeste d'un dataset publié.
- **Preuve** : barrière déterministe sur l'updateMany ; `dbState=SEALED`, `deletedPrefix` exécuté, `objectsRemaining=0`, `ipfsCid` posé ; lecture réelle ensuite « Intégrité Merkle invalide ». Négatif : annulation après SEALED → 409, zéro suppression.
- **Impact** : DoS définitif du dataset (aucun chemin de réparation), pas de fuite (GCM/SHA intacts).
- **Remédiation** : sauter `deletePrefix` quand `updateMany` rend `count === 0`, à l'image de `purgeExpiredUploads:271-276`.

### [MEDIUM] U3 — Clôture perdante écrase le manifeste du gagnant

- **Vecteur** : deux `complete` concurrents du même envoi. Le manifeste est écrit dans R2 **avant** le CAS `OPEN→SEALING` (`src/lib/sirius/chunked-upload.ts:480-486`) ; le perdant du CAS reçoit 409 mais son écriture persiste. Les morceaux ne sont contrôlés que par taille (`:203-216`), donc deux manifestes distincts de même géométrie passent tous les deux.
- **Preuve** : SHA stocké = SHA du manifeste B (perdant) ≠ SHA journalisé = SHA du manifeste A (gagnant) ; vrai `sealChunkedDataset` sur A puis vrai `chunkedTrainingSample` sur le stockage écrasé → « Intégrité Merkle invalide ». Négatif séquentiel : refus avant tout `put`.
- **Impact** : dataset scellé et publié définitivement illisible ; re-téléversement requis. Déclencheur plausible sans malveillance : réessai réseau, double onglet.
- **Remédiation** : n'écrire le manifeste qu'après un CAS gagnant (déplacer le `put` après l'`updateMany` et son `count === 1`).

### [MEDIUM] U5 — CSV multiligne : faux enregistrements dans l'entraînement

- **Vecteur** : `completeLines` découpe par `\n` sans état de guillemets (`src/lib/tee/chunked-sample.ts:124-135`) ; les bornes par morceau sont prises sur les premières lignes candidates, arrêt avant le guillemet fermant (`:186-201`) ; le repli vers le parseur strict n'a lieu que si l'échantillon est syntaxiquement invalide (`:202-208`). Un champ cité multiligne à cheval sur un morceau échantillonné, contenant des lignes au format du fichier, produit un échantillon valide contenant des enregistrements qui n'existent pas dans le fichier.
- **Preuve** : fichier 4 Mio accepté par le parseur strict et par le vrai scellement ; le vrai `chunkedTrainingSample` produit exactement 1041 faux `9,1,z` (x=9 absent des données réelles) ; l'entraînement réel consomme l'échantillon pollué. Négatif : sans champ cité, aucun faux enregistrement.
- **Impact** : le modèle livré s'entraîne sur des données fantômes — le Merkle root certifie le fichier, pas ce qui a réellement servi. Attaquant = fournisseur du dataset ; préjudice du côté emprunteur (qualité du modèle payé).
- **Remédiation** : découpe de l'échantillon par un parseur conservant l'état des guillemets ; le repli `prefixSample` ne couvre pas ce cas.

### [MEDIUM] F2 — Budget assistant : réservation de comptes, pas de montants

- **Vecteur** : route publique si activée (`src/app/api/assistant/chat/route.ts:62-75`). `reserveAssistantRequest` n'incrémente que `count` (`src/lib/assistant/daily-cap.ts:52-68`) ; la dépense n'est inscrite qu'après la génération (`:71-84`, route `:102/:117`). N requêtes admises en parallèle voient toutes `spentMicroUsd` sous le budget, puis chacune inscrit son coût réel.
- **Preuve** : vraies fonctions + stockage local implémentant les prédicats atomiques + vrai handler POST avec fournisseur simulé. 10 requêtes concurrentes admises, 16 000 µUSD/réponse (800 jetons de sortie, barème `src/lib/assistant/config.ts:48-53,63-68`) pour un budget de 10 000 µUSD : dépassement ×16, puis refus 429 au tour suivant. Témoin sérialisé : refus dès la 2e requête après 1 réponse (le stockage évalue bien le prédicat).
- **Impact** : dépassement du budget quotidien configuré, puis indisponibilité de l'assistant. Borné par les plafonds de requêtes, 3 tours d'outils et 800 jetons de sortie par appel.
- **Remédiation** : réserver atomiquement un montant couvrant chaque génération avant l'appel fournisseur, réconcilier réservation et consommation réelle (annulation comprise), contrôler les engagements avant les tours supplémentaires.

### [MEDIUM] F3 — KYB démo : révocation réversible en un clic ; expiration auto-choisie

- **Vecteur** : le parcours automatique refuse un compte bloqué ou révoqué (`src/lib/kyb/auto-invite.ts:274-283`), mais le parcours démo ne réutilise pas ces contrôles : `prepareDemoAttestation` lit le nonce courant sans vérifier `isBlocked`/`revoked` (`src/lib/sirius/kyb-demo.ts:63-108`), `submitDemoAttestation` ne teste que « déjà valide » puis appelle `attestWithConsent` (`:111-154`). Le contrat accepte l'attestation fraîche et écrase avec `revoked: false` (`contracts/src/SiriusKybRegistry.sol:190-202,273-285`).
- **Preuve** (registre v3 réel sur Hardhat local, deux vérificateurs) : parcours auto refuse 403 après révocation ; rejeu de l'ancienne signature refusé (garde nonce) ; réattestation démo passe avec une signature fraîche (émetteur inchangé, `isKybValid=true`). **F3-bis démontré** : le PUT soumet un `expiresAt` sans lien avec le POST — le sujet signe lui-même n'importe quelle échéance ≤ 729 jours au lieu des 30 préparés.
- **Portée** : instances de démonstration uniquement (`EVM_NETWORK=testnet` ⇒ mode démo, interdit sur mainnet par `src/instrumentation-node.ts:42-44`). La révocation automatique d'une attestation réémise par un autre vérificateur est aussi refusée (`auto-invite.ts:459-460`).
- **Remédiation** : appliquer les refus `isBlocked`/`revoked` aux deux étapes du parcours démo ; lier l'expiration soumise à celle préparée ; une réhabilitation reste une décision administrative explicite.

### [LOW] U2 — URL PUT réutilisable après scellement (statique, non reproduit)

`UNSIGNED-PAYLOAD` et `content-length` signé sans empreinte du corps (`src/lib/storage/r2.ts:25,125-175`) ; TTL 15 min (`src/lib/sirius/chunked-upload.ts:55`) ; `presignUploadParts` refuse non-OPEN (`:415-437`). Fenêtre : réutiliser une URL encore valide avec un corps différent de même longueur → écrasement détecté aux lectures (SHA/GCM) → DoS du dataset, pas de substitution silencieuse. Non reproduit faute de backend local validant SigV4 ; à confirmer sur vrai R2. Remédiation : écriture create-only effectivement signée ou version immuable des objets scellés.

## LOW / INFO hors reproduction

- **Branche fail-open latente** (`src/lib/tee/identity.ts:155-156`) : `bootDone === -1` accepte l'événement compose-hash sans `system-ready`, contrairement au commentaire `:118-121`. **Réfutée comme contournement** : `bootEventPayload:126` exige `system-ready` → pins `null` face à un pin présent → `matchesPinnedEvent` false (`src/lib/tee/quote.ts:159-162`) → refusé partout en production. Durcissement facultatif : `bootDone === -1 → false`.

## Zones vérifiées sans finding

- **TEE/RA-TLS** : certificat feuille épinglé (TLS 1.3, `ra-tls-client.ts:276-289`), quote liée au certificat par `report_data` (`quote.ts:240-242`), pins requis en production non-démo (`instrumentation-node.ts:85-93`), `SIRIUS_MASTER_KEY` interdite dans la CVM (`src/runner/config.ts:22`), bootstrap refusé (`ra-tls-evidence.ts:19`), capability HMAC TTL 60 s + nonce + scope, `SIRIUS_LOCK_AUTHORIZER` == compte de règlement re-vérifié on-chain (`deployment.ts:13-33`). Pins KMS optionnels côté enclave (`dstack.ts:69`) rattrapés côté site ; historique UNKNOWN borné au mode démo.
- **Contrats** (passe 1, lecture intégrale) : reentrancy, rejeu EIP-712 (chainId + verifyingContract + high-s rejeté), transferts exacts (fee-on-transfer rejeté), comptabilité pull-only, préimage non forgeable, KYB à époque et consentement — invariants tenus. `withdrawFor` permissionless = choix de liveness bénin.
- **Auth/session/CSRF** : challenge HMAC à nonce persistant consommé une fois, origine + `sec-fetch-site` sur toute mutation, comparaisons à temps constant, CSP nonce + `strict-dynamic`.
- **Règlement (autres chemins)** : double paiement packs/prolongations impossible (idempotence par clé + journal atomique) ; reçus liés loanId/chainId/escrow ; rejeu de signatures runner bloqué par registre persistant.
- **Risque documenté et accepté** (D-27/D-28/D-30) : une logistique reste clonable par décision seule — reproduit à 52 appels sous quota de 100, accord 100 % sur 10 000 points. Ce n'est pas un finding.
